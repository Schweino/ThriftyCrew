## capture-watchdog reads the start sync's two in-progress stages as a stage no real run passes through

`OPEN` `queue-sh-cr` `2-WAY` `RUNG1 BUILD`

**Source.** The same lane and day, read in grocery/capture-watchdog.ps1 (a landed library this lane does not edit),
section 2b "the run's OWN record". Its recognised in-progress stages are the literal list
`@('started','capturing','downstream','publishing')`, and any other stage short of `complete` raises
`RUN RECORD: capture-run [<kind>] left stage '<stage>', which is not a stage a real run passes through`.

**What W4.1 adds.** capture-run now writes four more stages: `syncing` (the start sync is running), `synced-handoff`
(a synced parent has handed off; the child overwrites the record with its own stages as soon as it starts),
`blocked-checkout` (exit 1 before any capture, paged) and `handoff-failed` (the child never ran, paged). The last two
are real findings and reading them as one is right. The first two are healthy in-progress stages, and a watchdog pass
that lands inside a long sync (the fetch alone is bounded at 3 x 300 s) or inside a handoff's first seconds would page
a false RUN RECORD. **What fixes it:** add `syncing` and `synced-handoff` to that list, under the same 90-minute age
bar the other in-progress stages meet, with a fixture for each in the watchdog's own self-test. Not done here because
the watchdog is W1.1's file.

## the abandoned-lock skip writes no status record, where the plan text says it writes skipped-locked

`OPEN` `queue-sh-cr` `2-WAY` `RUNG1 DOC`

**Source.** The same lane and day, plan W4.1 step 7: "write stage skipped-locked and exit 0, as a normal lock refusal
does". Built and measured in grocery/test-capture-run-sync.ps1's ORPHAN case: the check that skips reads the status
record's pid to find the live synced child, and capture-run's Write-RunStatus writes `pid = $PID` into the record of
its own kind. A skipper of the same kind that wrote `skipped-locked` would replace the child's pid with its own, so
the NEXT occurrence would find no live capture-run in the record, take the abandoned lock and run beside the child.
So the skip prints its SKIP line and exits 0 without writing the record and without releasing the lock (its exit
abandons the lock again, so the next occurrence asks the same question). **What is left:** plan section 6 W4.1 step 7
should say so, or Write-RunStatus should learn to keep another run's pid; the second is a larger change and was not
asked for.
