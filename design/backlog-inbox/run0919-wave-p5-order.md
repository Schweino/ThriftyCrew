## wave-publish p5 could refuse nothing since 2026-08-15, and its allergen check sat where no wave card exists yet

`NEEDS A RULING` `run-0919` `2-WAY` `RUNG1 RULING`

**Source.** A new finding from run 0919, not a backlog item. The I172/I173 agent (base 0465267ef) recorded under I173 that `meal-prep\pipeline\wave-publish.ps1` runs `audit-allergen-line` in P5, before E4's propagate builds any card, so every real wave would be refused at P5 ("no card" for a new recipe, "missing" for a republished pre-I144 card). The drill found that the prediction was wrong for a worse reason.

**What the drill found, measured at 0465267ef in a seeded worktree.** A `-DryRun -SkipGhostCheck -SkipGit` over a scratch run dir with a scratch ledger (no Ghost call is reachable under `-DryRun`, `TC_WRITE_JOURNAL` and `TC_STAGE_WRITES` cleared), one wave slug, `keto-cheeseburger-skillet`, whose built card predates I144. Result: exit 0, `P5 audit-allergen-line clean` and "every gate above passed". Run by hand as P5 runs it, the same gate exits 1 with its completion marker and names the slug `missing`. A census of all 10 P5 gates for that slug, each run exactly as P5 runs it: 9 of 10 truly clean, 1 (allergen) truly red, and P5 refused 0 of 10.

**Why. P5 has not been able to refuse anything since v2 shipped (7125ec86a, 2026-08-15).** `Invoke-Gate` wrote its two diagnostic lines with `Write-Output` and then `return $false`, so a red gate handed its caller an array (10 elements in the drill) and `if (-not (Invoke-Gate ...))` negated a non-empty array, which is `$false`. The refusal never ran, the diagnostics were swallowed by the `if`, and the loop printed `clean`. That covers all ten P5 gates (spec-contradictions, store-integrity, vocab-integrity, unbid, cost-plausibility, cost-line-coverage, ghost-field-limits, wave-blocker-headings, allergen-line, test-guards). A search of `meal-prep\runs` for any red-gate diagnostic line found 0, as it must when the line is swallowed, so **whether any published wave passed a red P5 gate is NOT measured and cannot be from the logs**. Other layers (the pre-audit's shared gates, propagate's own hard gates, the batch auditor) still ran.

**So the allergen ordering defect is real but was masked.** Fixing `Invoke-Gate` alone would turn it on and refuse every wave. Both are repaired together on branch `claude/wave-p5-order`, which is pushed and NOT on main.

**What the branch does.**
- `wave-publish.ps1`: `Invoke-Gate` returns ONE verdict object and writes nothing to the pipeline; the P5 loop is `Invoke-P5Gates`, a function the self-test drives over real child scripts; the caller prints the report and refuses. `audit-allergen-line` is removed from the P5 table.
- `propagate-recipes.ps1`: `Invoke-GatedPublish` runs `audit-allergen-line` in-process over the dirty slugs AFTER `build-cards` and BEFORE `engine\publish.ps1`, which it takes as a scriptblock; a refusal throws before the publish block is invoked, so no Ghost call follows and no stamp advances. `engine\publish.ps1` is now reached only through it.
- `wave-preaudit.ps1`: the I173 allergen check reads the card-rebuild check's scratch render (same build-card2, same spec) instead of `db\built`, since that fresh render is what the gate will judge. A stale or absent `db\built` card is no longer predicted as a refusal.
- `audit-allergen-line.ps1`: header and its wiring case now name propagate.

**Why this placement and not "build the cards before P5".** The guarantee is "no card publishes with a wrong or missing allergen line", and only one point sees the card that ships before it ships: between propagate's `build-cards` and its `publish`. A scratch build before P5 would check a different render made before E1 and E2 rewrite the spec, and would never see the collateral dirty specs propagate carries with a wave, nor a plain recost propagate that never met a wave. The placement copies the estate's own precedent: `feed-covers-published` and `audit-buy-label-plurals` sit in propagate for exactly the reason that the seven "Buy 2 8ozes" pages did not come through a wave. Cost: a fresh build always carries the line, so on today's code the gate is green on day one and fires only on a card build-card2 did not produce correctly.

**Verified on the branch.** Self-tests: wave-publish exit 0 (9 new cases: 5 MUST FIRE of which 2 pin the wiring, 1 CLEAN TWIN, 2 sub-assertions on the refusal's report and stop, 1 pin that the live P5 reads the verdict object), propagate-recipes exit 0 (6 new: 5 MUST FIRE of which 1 pins the live order, 1 CLEAN TWIN through a stub publish), audit-allergen-line exit 0 (23 of 23), wave-preaudit exit 0 (75 cases, blind=0; the drill constant moved 16 to 17). Broken once each, file md5-identical after every restore: `Invoke-Gate` put back to its 2026-08-15 shape with the loop negating it, 4 cases red with the red gate read as clean; the allergen condition in `Invoke-GatedPublish` replaced by `$false`, 3 MUST FIREs red with the stub publish called; the pre-audit pointed back at `db\built`, its 2 CLEAN TWINs red. The post-fix `-DryRun` drill over the same slug: exit 0, 9 P5 gates clean, no allergen line in P5.
