## invoke-pipelinecommit leaves the shared index holding a staged revert of everything it committed

`OPEN` `queue-7` `2-WAY` `RUNG1 BUILD`

**What is wrong.** `Invoke-PipelineCommit` in `lib/pipeline-commit.ps1` commits under a private index (a temp
`GIT_INDEX_FILE` seeded from HEAD), and never resyncs the checkout's real index afterwards. capture-run's own commit
stage does (`grocery/capture-run.ps1`, the block headed "RESYNC THE SESSION'S INDEX FOR WHAT WE JUST COMMITTED", which
runs `git reset -q -- <path>` for every path of the bot commit). The three lanes that commit through this function,
`graph/pipeline/nightly.ps1`, `meal-prep/pipeline/harvest-crawl.ps1` and `grocery/check-ad-cycles.ps1`, all run in the
shared main checkout.

**Measured on 2026-09-23 in a temp repo** (scratch probe, not committed; lib blob `e9a1d1aae281`, the W3.2 landing
state of the file). A lane commit that modified `a.json`, deleted `gone.json` and added `new.json` returned
`probe: committed 3 file(s)`, and the real index then read:

```
MM lane/out/a.json      a staged REVERT of the committed modification
AD lane/out/gone.json   a staged RE-ADD of the file the commit deleted
D  lane/out/new.json    a staged DELETION of the file the commit added (plus ?? for the file on disk)
```

So one plain `git commit` by a session in the main checkout undoes the lane's commit, and the `AD` rows are exactly
the resurrection shape the plan's addendum records for `cec9779a3` (three deleted files came back on disk and staged).
The autostash rebase that runs today restores content from that index, which is one way a deleted file comes back.

**What already copes with it.** W0.2's snapshot reads HEAD-tracks from git's index column, so an `AD` row is never read
as a deletion to hold, and an `MM` row a later run does not rewrite is held with a reset that restores HEAD's entry,
which equals the bytes on disk: a no-op.

**First rung.** Give `Invoke-PipelineCommit` the same resync capture-run has, after the private index is released and
only when the commit landed: `git reset -q -- <each path of HEAD's commit>`, never the working tree, never a path
outside the commit. MUST FIRE: after a lane commit that modifies, deletes and adds, `git status --porcelain` in the
temp repo shows none of the three as staged. CLEAN TWIN: a session's staged change on a path outside the commit is
still staged afterwards. The checkout sync of the same plan (W3.1, W4.2) reads staged changes as FOREIGN, so whoever
lands it should know that every lane commit leaves such rows today.
