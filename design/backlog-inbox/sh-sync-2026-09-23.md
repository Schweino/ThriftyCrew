## capture-run's post-commit index resync never resets a path the bot commit DELETED when git pairs it as a rename

`OPEN` `queue-sh-sync` `2-WAY` `RUNG1 BUILD`

**Source.** Lane `sync` of design/PLAN-bot-checkout-self-heal-2026-09-23.md (W3.1), 2026-09-23, while building the
addendum's "resync the real index for DELETED paths" requirement. Measured on origin/main at `cec9779a3` (the forced
daily commit the addendum is about), read-only:

    git show --name-only --pretty=format: cec9779a3      names grocery/out/untracked-quarantine/2026-09-23/graph/provenance/2026-09-22.jsonl
                                                         and NONE of the three deleted files
    git show --no-renames --name-only --pretty=format: cec9779a3
                                                         names graph/provenance/2026-09-22.jsonl,
                                                         grocery/out/browser-capture-due-2026-09-18.flag,
                                                         grocery/out/browser-capture-due-2026-09-20.flag and
                                                         grocery/out/throttled/family-fare-2026-08-31.throttled.json as well

`git show --stat -M --diff-filter=R cec9779a3` lists exactly four renames: the provenance move and the three deleted
files, each paired with a newly added file of similar content (`browser-capture-due-2026-09-18.flag` =>
`browser-capture-due-2026-09-22.flag`, `-09-20` => `-09-23`, `family-fare-2026-08-31.throttled.json` =>
`family-fare-2026-09-23.throttled.json`).

**What is wrong.** `grocery/capture-run.ps1:1159` resyncs the REAL index after its private-index commit with
`git show --name-only --pretty=format: HEAD` and one `git reset -q -- <path>` per name. `diff.renames` is on by default,
so a deletion that git pairs with an add is listed only under its NEW name, and the deleted path keeps its stale entry
in the real index. That is the mechanism behind the addendum's three resurrected files: the entries survived the resync,
and the push-time autostash restored them from the index to disk. It is not specific to that day: every rotating dated
file the pipeline deletes and re-creates (flags, throttled captures) is exactly the shape rename detection pairs.

**The repair.** `--no-renames` on that `git show`, in grocery/capture-run.ps1 (W4.2's file, not this lane's). Until then,
`Invoke-TcCheckoutSync -BotCommit <the commit just made>` (lib/checkout-sync.ps1 step 1g) resets exactly these leftover
entries, deletions included, and its self-test drives the capture-run shape above as its precondition case. W4.2 should
pass `-BotCommit` at the tail and fix line 1159 in the same change, so the two do not disagree about what was committed.

## The startup-file list does not include what the startup libraries themselves dot-source

`OPEN` `queue-sh-sync` `2-WAY` `RUNG2 DECIDE`

**Source.** Same lane, same day. `$script:TcCheckoutSyncStartupFiles` in lib/checkout-sync.ps1 is capture-run.ps1 plus
the eleven files an AST scan finds it dot-sourcing directly (the plan's W3.1 step 6 definition), and the self-test holds

grocery/capture-policy-lib.ps1 load lib/ledger-lock.ps1, which loads lib/event-bus.ps1 and lib/ledger-fixture.ps1;
lib/git-blob-lib.ps1 loads lib/git-repo-env.ps1 in its self-test; grocery/fanout-lib.ps1 loads lib/concurrency-probe.ps1.

**What is wrong.** A change to one of those alone does not set `startup_changed`, so the run after it executes the
stale copy for one run, which is the one-run lag G6 exists to remove, one hop down. The spellings the libraries use are
varied (`$__cvLibRoot`, `$script:PolicyRoot`, a `. $Lib` inside a self-test), which is why the scan reads only the
direct set and refuses a base it does not recognise rather than guessing.

**Options.** (a) Leave it: the transitive libraries changed rarely, and a one-run lag is the day before, never a wrong
tree. (b) Scan the closure, recognising the extra base spellings, and hold the literal list equal to that. (c) Make
`startup_changed` true whenever any `lib/*.ps1` or `grocery/*-lib.ps1` changed. Recommendation: (b), measured first by
counting how many of the last 30 days' commits touched a transitive library and no direct one.

## The plan's step 1d/1e and step 7 rows restore or quarantine files the sync may not touch; the lib now departs from both

**Source.** Skeptical review of lane `sync` (W3.1), 2026-09-23, findings 2 and 3, each reproduced in the lane's own

**What is wrong in the plan.** design/PLAN-bot-checkout-self-heal-2026-09-23.md line 637 says an owned path holding
markers or unmerged entries is "set aside, then `git checkout HEAD -- <p>`", with no vouching and no staging check, so a

so. An untracked file where upstream adds a path is IN-THE-WAY only under an owned path; outside them it is FOREIGN,
unless its blob already equals upstream's, when an index update carries it untouched.

**Ask.** Amend the two plan rows to match, so W4.1 and W4.2 are built against the rule the lib enforces.
