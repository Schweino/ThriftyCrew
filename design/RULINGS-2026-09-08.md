# Eight rulings, written up for Brad - 2026-09-08

These are the `NEEDS A RULING` items on `design/BACKLOG-course-findings.md`: **I38, I42, I55, I81,
I86, I91, I93, I97.** They are Brad's and nothing here decides them. What this file owes each one is
that it be **decidable in a minute** - the question in one line, the real options, what each costs if
it turns out wrong, and a recommendation that can be disagreed with.

**The criteria below were written BEFORE the eight were assessed**, which is the whole point of doing
it this way. A threshold chosen after seeing the case is a description of a decision already taken,
and the estate has the same rule for its own scorers (backlog E21). Each item is scored against these
separately, and the global judgement comes last - **dealbreakers first**.

| # | Criterion | Why it is a criterion here |
|---|---|---|
| C1 | **Does a wrong answer reach a reader?** | This is a live paid site. A wrong number on a page is a real cost to a real person, and understating is exactly as wrong as overstating. Any item scoring badly here is a dealbreaker regardless of the rest. |
| C2 | **Can it be undone?** | The estate has no undo layer on remote writes beyond `ops/revert-ghost-write.ps1`, and none at all on a member-data pull or a schema change to a 126 MB `graph.db`. |
| C3 | **What does it cost to run, in hours or money?** | One person, one box. GPU hours are nights, not minutes. |
| C4 | **What is the cost of NOT deciding?** | Several of these are cheap to defer and one gets strictly more expensive every month. That asymmetry is the most decision-relevant fact in this file. |
| C5 | **Does anything downstream unblock?** | Two of the eight are prerequisites for items sitting behind them. |

**A note on how these got here.** Seven of the eight are genuinely one-way doors by the reversibility
sort - they spend money, GPU hours, a precedent, or a member-data pull that cannot be un-pulled. The
eighth, **I42, is not**: its first rung is a plain read, and it is flagged `2-WAY` `RUNG1 READ`
because the read can happen without any ruling at all. It is in this file because the *decision* the
read informs is still Brad's.

## The one that is time-sensitive, so it is first

### I97 - may anything read Ghost's member data at all, and if so may a per-member row touch disk?

> **NOTHING WAS PULLED, EXPORTED OR WRITTEN.** No member row, no email, no count, not even to a
> scratch file. Member emails have never touched this repo and this session did not change that. What
> follows is the question, prepared from code already in the tree.

**The question, in one line.** This is a live paid membership and **nobody knows what fraction of
each month's signups is still paying a year later.** May a read-only script pull `id, created_at,
status, labels` from the Ghost Admin API, and if so, may any per-member row be written to disk?

**What is already true, read from the tree rather than assumed.** Every Ghost members call here is
transactional, not analytic: `worker/index.js:146,170` (find one member, PUT labels),
`worker/index.js:328,391` (read `member.status` to gate paid content),
`grocery/send-price-alerts.ps1:103`, `grocery/send-friday-digest.ps1`,
`.claude/skills/lesson/grant-founder.ps1:42-48`. **`created_at` is never read for a member anywhere.**
There is no member export, no cohort table, no retention curve, no churn figure and no LTV number in
this repo. The Admin key already exists, so no new credential is involved.

**The options.**

| | What it is | If it is wrong |
|---|---|---|
| **A. No pull at all.** | Retention stays unknown. | Every acquisition-side item in the backlog and every SEO finding sits on top of a number nobody has. If month-1 retention is below the floor, the layer being worked is above the broken one. |
| **B. Aggregate only.** A read-only script pulls in memory, buckets by signup month against current status, and commits **only the bucketed counts**. No per-member row ever touches disk. | A bug that writes the raw response to a log or a temp file. That is a real risk and it is the one to guard, not the API call. |
| **C. Per-member rows on disk**, in a gitignored path. | Member emails enter the machine's filesystem and one `git add -A` puts them in a public repo. The estate has a standing rule against `git add -A` precisely because that has happened with other data. |

**Cost if wrong (C1, C2).** B and C are **one-way in the privacy direction**: data that has been
written can be deleted, but data that has been *seen* by a process that logged it cannot be un-seen,
and a repo push is not retractable. A is one-way in the opposite direction only in that time passes.

**Recommendation: B, with three conditions**, and B is worth doing because A's cost is real:

1. the script aggregates in memory and **writes only `(signup_month, status) -> count`**;
2. it never writes a temp file, and its output path is asserted before the first API call;
3. it is the only caller, run by hand, and it prints its denominator.

**C is not recommended at any price.** The analysis B supports does not need a per-member row.

**Why this one is first: I98 makes it decay.** Ghost gives current status, **not a status history**.
A pull today can say how many January signups are still paid but cannot distinguish someone who
cancelled in month 2 from someone who cancelled in month 8 - so it yields **one endpoint per cohort,
not a curve**, and the curve shapes are where all the diagnostic value is. The fix is a monthly
committed snapshot of aggregate counts, **and every month it is deferred is a month of curve that can
never be recovered.** It is a few dozen bytes a month and needs no analysis built on top of it.
**Deciding A is a legitimate answer; deciding nothing is the one option that costs something every
month.**

**What unblocks (C5).** I98 and I99 are both `1-WAY BLOCKED` on this and cannot move until it is
answered.

## The two that are cheap to say yes to

### I38 - do the three `Get-Random` refusals extend to a seeded test-input generator?

**The question, in one line.** `Get-Random` appears in exactly three files here and **all three are
refusals**; may a seeded generator produce hostile inputs for the parsers, or does the estate read
those three as a standing ban?

**The refusals are each correct for what they refuse**, and that is the crux.
`grocery/build-verification-sample.ps1` ("DETERMINISTIC, NOT RANDOM"), `grocery/test-auditors.ps1`
("Get-Random would silently make every past worklist unreproducible") and `lib/ghost-lib.ps1` (attempt
index as jitter) are all refusing unreproducible **work selection**. **None of them is an argument
against generated test input, because a seeded generator IS reproducible** - record the seed beside
the failure and the case replays byte for byte, which is exactly what the deterministic-sample rule
was protecting.

**Why it matters here.** 255 `.ps1` files mention `ConvertFrom-Json` across 819 matching lines. A grep
for self-test cases whose `MUST FIRE` line mentions malformed, truncated, corrupt, empty or invalid
input returns **6** - a lower bound from one narrow pattern, not a census, and the order of magnitude
is what the item rests on. This estate parses text it did not author all day.

**What it costs (C3).** Small, and smaller than when the item was filed. **Crash-or-hang is the
entire oracle** at the boundary this is scoped to: an error is a pass, an assertion violation is a
pass, only a crash or a hang is a finding. So the build is a generator and a `try`/`catch`, not a test
suite.

**Two conditions if it is a yes**, both from the estate's own scars:

- **whatever gets built prints the number of draws that REACHED the assertion.** A property-based test
  can pass having run nothing - guard clauses rejecting out-of-envelope draws can reject nearly every
  draw while the run reports success. That is `<NAME>-COMPLETE`'s reason, one floor up.
- **scope it to the boundary where outside bytes first arrive** - the capture lanes and the feed
  readers. Most of the 255 parse points read files this estate wrote one stage earlier over the
  git-bus, where nothing is adversarial and a fuzzer finds nothing. An item that fuzzes everything
  spends its budget on the wrong 200 files.

**Recommendation: rule that the three refusals do NOT extend to a seeded test-input generator, and
then do I65 FIRST.** I65 is the consistency oracle - run the previous version of a parser and the new
one over the same real input and require identical output - and **it involves no randomness at all, so
it needs no ruling and is already `2-WAY`.** If the objection to I38 is the `Get-Random` question,
I65 sidesteps it entirely. **Cost of not deciding: near zero**, because I65 can proceed either way.

**Still unsolved by anything available:** shrinking a failing input to a minimal one, which is what
makes a fuzz finding actionable rather than a 40 KB blob. And there is no `hypothesis` package
installed - the grep that suggests otherwise matches only numpy's and anyio's vendored test files.

### I42 - is any capture lane's raw response worth keeping, and at what disk cost?

**This is the one whose first rung needs no ruling at all.** It is `2-WAY` `RUNG1 READ`: for each
capture lane, answer one question - *after the transform, does the raw source response still exist
anywhere on disk or in git?* One table, one row per store. **That read was not done in this session
and it is the cheapest unstarted thing in this file.**

**The question, in one line.** For any lane where the answer is "no", is raw retention worth its disk
cost?

**Why it is a real question rather than an obvious yes.** The estate runs **ETL** in `grocery/` (pull,
normalise, write the board; the transform is re-run daily instead of the raw being kept - which is why
`known-wrong.json` exists) and **ELT-ish** in `graph/` (events ingested as they arrived, derivations
computed from them, so a derivation change can be re-run over history). Neither `ETL` nor `ELT` appears
in any first-party file. That is a real architectural split nobody has named.

**The axis that makes it matter, and it is the one the courses never name: is the source
RE-ACQUIRABLE?** A shop's shelf price on a given morning **is not re-acquirable at any price.** So
every point in the capture lane where a raw response is parsed and discarded is a place where evidence
is destroyed and nobody decided to destroy it.

**Cost if wrong (C1, C2).** Discarding is the one-way direction, and it happens every day by default.
Keeping is reversible and costs disk in a repo the ~07:00 bot commits whole - which is I36's territory,
now resolved as *keep forever, deliberately*, with a stated ~10 MB trigger.

**Recommendation: do the read first, then decide, and expect the read to shrink this.**
`grocery/out/` already holds a lot of intermediate JSON, so the answer may be "mostly yes, by
accident", which turns this into a documentation item. **Cost of not deciding: one day of raw
capture per day, permanently** - low per day, unrecoverable in aggregate.

## The two about money and GPU hours

### I55 - is the 27B adjudication fine-tune still wanted at all?

**The question, in one line.** Spend **17-25 hours of continuous local GPU across nights**, or ~1 hour
and ~$10 on a cloud A100, to fine-tune the local 27B for adjudication - or drop it?

**What makes this worth asking rather than obvious.** Two previous course runs asked *"does this change
what `finetune_reranker.py` should do?"*, answered no on sound reasoning, and **recorded the verdict as
if it covered the estate. It does not.**
`design/MEASURE-local-finetune-feasibility-2026-08-22.md` is a **measured** QLoRA study of the local
27B on this box, with working probes: 57.3 tok/s, 8.31 h per epoch, peak 15.59 of 15.92 GiB, 58.4M
trainable params at r=8, and a corpus builder emitting 3,198 rows from `graph/gold/gold.jsonl`. **Three
course runs have discussed LoRA here and none cited it.** The motive they could not find is written
down and quantified: 26.9B parameters against a 15.92 GiB card, where PEFT is not a preference but the
only arrangement that fits.

**The honest counter, from the feasibility doc's own section 10: the work is unfinished.** The
commodity-family holdout split **does not exist**, and without it a training run cannot report a
cold-start false-MATCH rate against the stock-27B **29% baseline** - which is the entire point of the
exercise. **So a yes today buys a run whose result could not be scored.**

**Cost if wrong (C3, C4).** Nights of GPU that cannot overlap the 07:00 semantic sweep, or $10 and an
hour. Reversible in the sense that an adapter can be deleted; not reversible in the sense that the
nights are spent.

**Recommendation: NO for now, and the reason is sequencing rather than merit.** Build the holdout
split first (that is **I56**'s territory and I56 is `2-WAY`, blocked only on this ruling), then
re-ask. A training run with no way to score its result against the 29% baseline is the thing
`.claude/rules/measurement.md` exists to prevent. **Cost of not deciding: zero.** Nothing decays.

**Section 7's rulings stand and are not up for revisiting:** detached LoRA adapter, never a merged
GGUF; holdout by commodity family; reject-only kept afterward; thermal watchdog on any local run.

### I86 - is a `final`-style `Invoke-Guard` wrapper worth touching 793 call sites?

**The question, in one line.** The `<NAME>-COMPLETE` obligation is a **convention honoured
independently at 793 call sites across 119 files**, backed by an audit that catches a violator *after*
it has already shipped a silent detector. PowerShell can make it structural with a scriptblock
wrapper. Is that worth doing?

**What is measured.** 793 `Write-GuardComplete` call sites, 119 files;
`grep "function Invoke-Guard\|function Invoke-Detector"` returns **zero**. `lib/guard-contract.ps1`'s
own header records **five separate incidents** of the shape it exists for - ff-carry throwing on its
report line for weeks, the cloud gate standing down 13 days reporting SUCCESS, reanchor-all crashing
between halves, store-integrity and batch-ledger crashes indistinguishable from clean.

**Three things need deciding and none is small:**

1. **Is 793 sites worth touching at all?** The current design works and is audited. *"Leave alone"* is
   a legitimate answer for a convention that has held.
2. **A wrapper changes the failure mode rather than removing it.** A guard that forgets to *use*
   `Invoke-Guard` is the same silent hole one level up, so the audit is still needed. The gain is that
   the obligation moves from **793 sites to 119**.
3. **`Write-GuardComplete` must never fire inside a `-SelfTest` branch or before the work is done**,
   and that file already documents a PS 5.1 dot-sourcing trap (`param()` running in the caller's
   scope) a wrapper would have to be checked against.

**Cost if wrong (C1, C2, C3).** Reaches no reader. Git-reversible in principle, but **a partial
migration is worse than none** - a tree where some guards are wrapped and some are not is harder to
audit than either pure state, and that is what makes this one-way in practice rather than in git.

**Recommendation: the cheap first step, not the sweep.** Wrap only the handful of guards that have
actually thrown mid-run, leave the other 700-odd, and **measure whether the wrapper survives contact
with the self-test paths** before anyone proposes a migration. If it does not, the answer is
"leave alone" and that is a good outcome. **Cost of not deciding: zero.**

## The two about a shape rather than a task

### I81 - should the recall hooks record their own duration, and at what resolution?

**The question, in one line.** Two of the three numbers worth having need **no new instrumentation at
all** - offers per turn, and consulted over offered, both derivable from log streams already being
written. Only **hook wall time** needs a new field. Add it, or not?

**Why it needs deciding BEFORE any data exists, which is the only reason it is a ruling.** A
histogram's resolution is fixed by its bucket boundaries **at instrumentation time and cannot be
improved afterwards.** In a per-event `.jsonl` there is no reason to pre-bucket at all, so the ruling
is really one line: **record the RAW duration per row, never a mean.** A mean is the one shape that
cannot be un-aggregated - this estate's own one-row-per-case rule (E24) wearing a different coat.

**The actual cost, and it is the whole objection (C3).** It is the only one of the three that touches
**the hot path of every tool call.** The recall hook's cost is already known to be dominated by
numpy's import at 66 ms against a 0.3 ms cosine pass, so a timestamp either side is noise by
comparison - but "noise by comparison" on every tool call is still a claim somebody should agree to.

**Cost if wrong (C1, C2).** Reaches no reader. Fully reversible - delete the field. The **one-way part
is the resolution**, and the recommendation removes that: raw values can always be bucketed later,
buckets can never be un-bucketed.

**Recommendation: YES to the two that need no instrumentation, and YES to the duration field on the
condition that it records the raw value.** Take the two free ones first regardless: they cost nothing
and they answer *is the recall loop earning its place*, which is the question behind all three.
**Cost of not deciding: small but real** - every day without the field is a day of durations that
cannot be recovered, the same shape as I98 at much lower stakes.

### I93 - is *a control constant that may only move one way needs a rate limit and a plausibility bar* a shape worth naming?

**The question, in one line.** `lib/ratchet.ps1` learned this the expensive way; `promote_aliases.py`'s
hold mechanism is the estate's **other** one-directional actuator and shares none of that machinery.
Is there a general shape here, and if so does it become a **third caller of `lib/ratchet.ps1`**, a
**documented convention**, or a **`run-gates` detector**?

**What is measured.** `lib/ratchet.ps1` exists because four audits each lowered a high-water mark
unconditionally, so a broken detector finding nothing would record 0 as a permanent ceiling and print
"PASSED and TIGHTENED" forever. `Test-RatchetMove` now refuses a fall to zero and a fall larger than
`-MaxDropPct` (default 60), keeps the old baseline, and reports. **That is a rate limit on a
one-directional actuator plus a sensor plausibility check, and it is exactly right.**
`promote_aliases.py` can only ever withhold MORE. It has a per-run baseline check but **no rate
limit**: one degraded guard run that hard-fails naming many commodities would record a hold for each
of them, permanently, in a single pass.

**The three options and what each costs if wrong.**

| | If it is wrong |
|---|---|
| **A third caller of `lib/ratchet.ps1`** | Couples a Python corrector to a PowerShell library across the runtime boundary `docs/RUNTIME-MAP.md` exists to document. Real cost, and the one nobody has priced. |
| **A documented convention** | Free, and unenforced. It will be honoured until the next author does not read it. |
| **A `run-gates` detector** finding one-directional state writes with neither guard | Cheapest to write and **the most likely to go stale**: it is a pattern matcher over source and would be unsound by construction, which - as of today - it would at least have to say out loud in its header. |

**Cost if wrong (C1, C2).** Reaches no reader. All three are git-reversible. The one-way part is that
**naming a shape sets a precedent that gets quoted**, and a convention nobody enforces is worse than
no convention because it reads as coverage.

**Recommendation: name the shape as a convention, and do NOT build the detector yet.** Then fix the
one instance that has a live cost - **I92**, the promotion holds, which is `2-WAY` and needs no ruling
for its first rung. `promote_aliases.py`'s docstring says 141 aliases promoted clean and **15 held**;
those 15 are a standing, invisible loss on the identity graph, held against the state of a board that
has been rebuilt roughly eighteen times since. **Cost of not deciding: low**, but it rises with each
new one-directional actuator anybody adds.

**Adjacent and unowned, part of the same question:** the estate has **no register of its control
constants**. `$script:BoardStaleHours = 26` and `$script:NeverRanGraceHours = 30`
(`grocery/capture-watchdog.ps1`), `$REARM_DAYS = 14` (`grocery/check-ad-cycles.ps1`) and
`-MaxDropPct 60.0` (`lib/ratchet.ps1`) are all tuning parameters of correcting loops, each declared
locally with a good comment and **none of them listed anywhere together**. `sidecar/THRESHOLDS.md` is
the precedent for what such a register looks like and it covers score spaces rather than these.

## The one about a credential

### I91 - does the estate want a rotation procedure for the `/notify` shared secret at all?

**The question, in one line.** `X-Notify-Auth` is the **SHA-256 hex of `GHOST_ADMIN_KEY`** and the
Worker recomputes the same value. The key itself never travels, which is the point of the design and
is a real property. But the derived credential has **no expiry, no recorded rotation procedure, and no
revocation independent of the admin key** - so rotating it means rotating the Ghost admin key, **which
is also what publishes every recipe card.**

**So the blast radius of a rotation is the whole publish lane, and the practical consequence is that
rotation never happens.**

**The options.**

| | What it costs if wrong |
|---|---|
| **A. Accept it.** One person, one machine, a long-lived shared secret between two systems Brad owns. | If the admin key ever leaks, `/notify` is compromised too and there is no way to revoke one without the other. `/notify` sends email to real people. |
| **B. A second, `/notify`-only secret independent of the admin key.** | A second secret to store and a Worker deploy. Cheap. Removes the coupling entirely and makes rotation a thing that CAN happen. |
| **C. A client-credentials grant against an identity provider with short-lived tokens.** | Real, and it is **a service Brad would have to run**. Disproportionate for one Worker route. |

**Cost if wrong (C1, C2).** C1 is the reason this is not a shrug: `/notify` reaches a member of the
public by email. C2 is the crux - **B is the option that makes the situation reversible**, which is
usually the right buy when the current state's defining property is that a correction is too expensive
to make.

**Recommendation: B, and only as far as writing down the procedure.** A `/notify`-only secret plus a
recorded rotation procedure. **Do not do C.** **A is defensible** and is not a bad answer - but note
that A is what is in force today by default rather than by decision, which is the same
unstated-forever shape I36 just resolved for the logs.

**Related and unowned:** no skill in the store owns service identity and access control. `OAuth`,
`OpenID` and `JWT` are clean no-matches over 1,350 sections; `security-craft` is scoped to adversarial
input against LLM systems and its own "does not own" section says so.
