### 3b. Family Fare coverage - TWO SEPARATE FAILURES, do not conflate them  **FABLE**

Rewritten twice on 2026-07-30. The second rewrite was my error and is worth recording: I measured the API
during a FRESHOP MAINTENANCE WINDOW, concluded "we are not rate-limited in the way everyone assumed", and
generalised a one-afternoon artefact across thirteen days of history it cannot speak to. Brad spotted the
maintenance notice. Separate the two:

---
**3b-i. 2026-07-30 afternoon: total shutout = FRESHOP MAINTENANCE. Nothing to fix on our side.**
Every `q=` search returned HTTP 400 while `/stores/6401` and `/products` browse (no `q`) stayed 200, a valid
session token made no difference, and - the tell - **the storefront's OWN search said "We're sorry. No
products were found with the given search criteria."** in a real browser with a store selected. It also
explains the timing nothing else did: `q=` worked at 09:00 for 788 rows and refused a few hours later.
No sharding, pacing or retry strategy would have helped. The correct response to this failure is to STOP,
which the estate now does (see FIXED below).

**3b-ii. 2026-07-17 -> 2026-07-29: PARTIAL pulls. Still unexplained. This is the real backlog item.**
Those runs returned 788-963 FRESH rows, not zero - partial is a different failure from refused, and
maintenance does not account for it. Contributing factors known so far:
  - the 9-minute wall-clock cap truncated ~500 terms mid-list (both 2026-07-30 morning runs hit it), and
  - a 2026-07-28 probe showed 20 terms at 200ms succeeding while a second burst came back empty, which is
    real evidence of a per-window request budget.
**Retest once maintenance clears, before designing anything.** The puller now reports status codes, so one
run answers it: if terms come back 200-with-0-items the store genuinely lacks them; if 400s appear again
after N successful terms, the volume story is confirmed and sharding `commodity-search.json` across the day
is the fix (merging via the carry-forward path fixed in item 3, alerting only when a full day comes up short).
**Why Fable:** shard boundaries decide whether one store's prices come from six different times of day, and a
plausible-looking wrong answer here silently poisons every FF cell - see the `search=` trap below.
---

**A TRAP TO AVOID REGARDLESS OF ANY OF THIS.** Using `search=` instead of `q=` returns HTTP 200 and 25 items
and looks like the fix. The parameter is silently IGNORED: the identical 25 default products come back for
milk, bananas, sour cream and ground beef. Shipping it would match every Family Fare commodity against one
default list. Only caught by checking whether results differed per term.

**Reference - what the API returned during the maintenance window (NOT evidence about normal operation):**
| request | result |
|---|---|
| `/1/stores/6401` | 200 |
| `/1/products` with NO `q` (browse) | 200, real items |
| `/1/products?q=milk` | **400** |
| same + a valid session token | **400** |
| same + `search_option_id=product` (what the storefront's own URL carries) | **400** |
Useful only as a fingerprint of what a Freshop outage looks like from our side: search 400s while browse and
store metadata stay 200. If that pattern appears again, check Freshop status BEFORE touching our code.
`/products/ads?q=` kept working throughout, which is why "q was removed" looked briefly plausible - it was not.

**ALREADY FIXED (2026-07-30), and both matter MORE during an outage, not less:**
- The puller no longer spends its whole budget proving it is refused. It aborts after 30 consecutive empties
  from a cold start (nothing ever ingested) or 60 mid-run, and skips the recovery passes, which exist to
  re-ask rate-limit victims and are the same mistake twice when nothing is being served. Measured 90s against
  1,803s on the identical shutout. Hammering an API 526 times through a maintenance window is exactly the
  behaviour you least want.
- `Get-FreshopItems` no longer swallows the status code. A refusal and a genuinely-not-carried term used to be
  byte-identical empty arrays, so the run reported "526 terms still empty" for a condition that had a
  specific, published cause. It now prints `API said: HTTP 400 x64`. Had that existed in the morning, the
  first run would have pointed straight at a status page instead of thirteen days of inferring a throttle.
